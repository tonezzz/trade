# Configuration Management

This document explains the configuration management approach for the trade project infrastructure.

## Single Source of Truth (SSOT) Approach

This project uses a **Single Source of Truth (SSOT)** pattern for infrastructure configuration to eliminate redundancy and prevent configuration drift.

### Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                    SSOT (Documentation)                     │
│  config/infrastructure.yml                                  │
│  - Authoritative source for all infrastructure settings     │
│  - Human-readable and well-documented                       │
│  - Contains all machines, servers, and configurations       │
└─────────────────────────────────────────────────────────────┘
                              │
                              │ Deployment Scripts
                              ▼
┌─────────────────────┐              ┌─────────────────────────┐
│  Runtime Configs    │              │  Validation            │
│                     │              │  scripts/validate-      │
│  - Remote server    │◄─────────────│  configs.sh             │
│    config.yaml      │              │                         │
│  - Devin CLI        │              │  Checks consistency     │
│    mcp_config.json  │              │  and reports drift      │
└─────────────────────┘              └─────────────────────────┘
```

### SSOT File

**Location**: `config/infrastructure.yml`

**Purpose**: Authoritative documentation and source for all infrastructure configuration

**Contains**:
- Global infrastructure settings
- Machine definitions (tony-omen, tony-dell)
- MCP server configurations
- Network configuration
- Security settings
- Monitoring and health checks
- Backup schedules

**Important**: This file is the **documentation SSOT**. Runtime configurations exist in their respective locations and are deployed from this SSOT.

### Runtime Configurations

#### 1. Remote Server Config
- **Location**: `/home/tony/mcp-remote-exec/config.yaml` (on tony-dell)
- **Purpose**: Configuration for the MCP remote execution server
- **Deployed by**: `scripts/deploy-mcp-config.sh`

#### 2. Devin CLI MCP Config
- **Location**: `~/.config/devin/mcp_config.json`
- **Purpose**: Configuration for Devin CLI to connect to MCP servers
- **Generated by**: `scripts/generate-mcp-configs.py`

## Scripts

### Deployment Scripts

#### deploy-mcp-config.sh
Deploys MCP server configuration from SSOT to the remote server.

```bash
./scripts/deploy-mcp-config.sh
```

**Syncs to remote server**:
- Security settings
- Allowed directories
- Server configuration
- Allowed commands

#### generate-mcp-configs.py
Generates Devin CLI MCP client configuration from SSOT.

```bash
python3 scripts/generate-mcp-configs.py
```

**Generates for Devin CLI**:
- remote-exec-tony-dell
- playlive.tony-dell
- mcp-gpu

### Validation Script

#### validate-configs.sh
Validates consistency between SSOT and runtime configurations.

```bash
./scripts/validate-configs.sh
```

**Validates**:
- SSOT file structure
- Remote config sync status
- Local MCP config sync status

## Workflow

### Making Configuration Changes

1. **Edit the SSOT**
   ```bash
   vim config/infrastructure.yml
   ```

2. **Validate changes**
   ```bash
   ./scripts/validate-configs.sh
   ```

3. **Deploy to runtime configs**
   ```bash
   ./scripts/deploy-mcp-config.sh
   python3 scripts/generate-mcp-configs.py
   ```

4. **Verify deployment**
   ```bash
   ./scripts/validate-configs.sh
   ```

### Change Examples

#### Adding a new allowed command
```yaml
# config/infrastructure.yml
mcp_servers:
  remote_exec_tony_dell:
    allowed_commands:
      - /usr/bin/python3
      - /usr/bin/docker  # Add this
```

Then run:
```bash
./scripts/deploy-mcp-config.sh
```

#### Updating MCP server endpoint
```yaml
# config/infrastructure.yml
mcp_servers:
  playlive_tony_dell:
    endpoint: "http://192.168.1.42:9231"  # Change this
```

Then run:
```bash
python3 scripts/generate-mcp-configs.py
```

## Benefits

1. **Single source of truth** - No more guessing which config is correct
2. **Automated deployment** - Scripts ensure consistent deployment
3. **Validation** - Detect drift before it causes issues
4. **Documentation** - SSOT serves as living documentation
5. **Version control** - Track all configuration changes in git
6. **Reproducibility** - Easy to recreate configurations

## Best Practices

1. **Always edit the SSOT first** - Never directly edit runtime configs
2. **Validate before deploying** - Run validate-configs.sh to catch issues early
3. **Test in development** - Make changes in development environment first
4. **Document changes** - Add comments in infrastructure.yml explaining why
5. **Run validation periodically** - Detect configuration drift

## Troubleshooting

### Configuration Drift Detected

If `validate-configs.sh` reports drift:

1. Identify which config has drifted
2. Check if manual changes were made to runtime configs
3. Re-deploy from SSOT to restore consistency
4. Investigate why drift occurred

### SSH Connection Issues

If `deploy-mcp-config.sh` fails to connect:

1. Test SSH manually: `ssh tony@192.168.1.42`
2. Check SSH key configuration
3. Verify network connectivity
4. Check firewall rules

### Service Won't Start After Config Change

If MCP service fails after deployment:

1. Check config syntax
2. Review service logs: `ssh tony@192.168.1.42 'journalctl --user -u mcp-remote-exec.service'`
3. Restore from backup if needed
4. Validate the change in SSOT
